# Translation cost

**What it shows.** What to pay translators and proofreaders for the period, per member and language. **Translation & Post-editing** splits translated source volume into No match, TM match, MT match, AI match and Other translations match rows, each with its rate and price; **Proofreading** prices approvals; Total adds both. **Savings (TM, MT and AI)**, **Weighted** and **Auto-translated** are informational. My activity (Enterprise) and My Contribution (crowdin.com) are this report limited to the viewer's own work. To turn a result into figures (spend, price per word, cuts, before and after, AI, what repeat translators or source changes cost), read `references/reports/translation-cost-figures.md` after this file.

**What it is not.** The figures are priced at the request's rates when the report is generated, never taken from payments or invoices: say 'priced at these rates', never 'what you paid'. Not in it: the AI provider's bill (`references/reports/ai-usage.md`), MT engine fees (Crowdin records none), hourly work (Time spent), the subscription and vendors' invoices. A connected vendor (Enterprise) is one technical member named after the vendor organization: its work is priced at your rates, its linguists are not visible, and it arrives with a TM match only, so it lands in TM rows or No match.

**Settings that change the result.**
- Date range, or Tasks for task mode. Languages (through the API: one language at project level, none at workspace level), members, files, folders and branches, labels, the Workflow step filter (Enterprise project), projects (workspace). Group by changes only the layout.
- Unit, currency, Full translation and Proofread rates, custom rates by member and/or language.
- Net Rate Schemes: TM (perfect, 100%, ranges from 40%), MT, AI and Other translations (ranges from 1% to 100%).
- **Use category-based approval rates**, **Exclude approvals for edited translations**, **Use specific categories for auto-translations**, **Use edit distance for TM Net Rate Scheme**. On the page they start from the saved rates or the rates template applied; with nothing saved, the first three are on and the last off (rates saved before these options existed load the first off and the next two on; a new rates template starts with all four off). Through the API all four default to off. Crowdin's documentation (checked November 2026) says Exclude approvals for edited translations and Use specific categories for auto-translations are always on from January 4, 2027: treat both as on when an archive generated from that date, or the report's documentation section, no longer lists them; an older archive without them was generated before they existed, so they were off; when it matters and you cannot tell, ask. A scheme without `useCategoryBasedProofreadRates` or `useTmEditDistance` was generated without them.

**Generating it through the API.**
- A project uses `translation-costs-pe` (`generate_report_translation_costs_post_editing`); a workspace or the organization uses `group-translation-costs-pe` (`generate_group_report_translation_costs_post_editing`, `generate_organization_report_translation_costs_post_editing`). Generation is asynchronous: poll the matching `check_*_report_generation_status` tool, then download the result, in `json` for computing.
- Required: `unit`, `currency`, `baseRates` (`fullTranslation`, and `proofread` unless `useCategoryBasedProofreadRates` is true), `individualRates` (may be `[]`) and `netRateSchemes`. A row's `matchType` is `perfect`, `100` or a range such as `99-82`; its `price` is a fraction of the Full translation rate (0.3 = 30%, 1 = 100%), although the API reference labels it '%': a price of 30 is accepted and prices the row at 30 times the full rate, so convert what the user types. When `aiMatch` is left out, the MT scheme is copied into it. Custom rates may name only current members: when copying an archive's rates, drop the rows of members who have left, or the request is rejected, and say so.
- The four options are `useCategoryBasedProofreadRates`, `excludeApprovalsForEditedTranslations`, `preTranslatedStringsCategorizationAdjustment` (Use specific categories for auto-translations) and `useTmEditDistance`, all false unless passed. An archive's `scheme` uses the same keys: copy them from it or from the template the user prices with, and never present a value you did not read as the user's setting.
- Workspace and organization take `projectIds` (empty means every current project of the scope), `userIds`, `taskIds`, `groupBy` (`user`, `language` or `project`) and dates, and no language, file, branch, label or workflow step filter: `languageIds` is silently ignored and `languageId` is rejected, so generate for all languages and take the language from the result. A project takes one `languageId` and the file, branch, label and workflow step filters. `templateId` is ignored at every level: pass the rates themselves.
- Dates are ISO 8601: an explicit offset (`+02:00`) is honoured, a date without one is read as UTC. Send the user's whole days.
- Every API generation is saved to the report archive, where other managers see it, unless `skipArchiving` is true, and a manager's archived task-mode run replaces the listed tasks' Actual cost. Pass `skipArchiving: true` unless the user asked to keep the result.
- Runs with the same report name and scope wait for each other, so one run per month or per project takes a while.

**How it counts.**
- It reads its record of actions, not the current translations.
- *One paid translation per person, string, language, plural form and source version.* Saving again does not pay again; the date and the match values stay from the first save. If the source text changes, the new version is paid again.
- *Pre-translations are never paid.* TM, MT or AI pre-translation, manual or automatic, shows only in Auto-translated, under the account the pre-translation ran under. Auto-translated is not split by engine or prompt: TM, MT and AI pre-translations are one volume. Automatic approvals (TM pre-translation with auto-approve, AI Pipeline auto-approve) are approvals by the account that ran them and are paid unless Exclude approvals for edited translations is on; nothing in the report says whether a person or a run approved.
- *Matches, recorded at the first save in the Editor:* **TM match** is measured in one of two ways, chosen by **Use edit distance for TM Net Rate Scheme**. With the option off, it is how similar the **source** is to the best TM suggestion Crowdin showed this translator for the string (or, if it showed them none, the best one shown to anyone for that string), whatever the translator then saved, so even a translation unlike every suggestion gets that TM row. With the option on, it is how similar the **saved text** is to the closest translation among the TM suggestions in this translator's Editor at their first save, whichever one they used: a TM translation saved unchanged is 100%, and a text unlike all of them falls below the TM rows. **MT**, **AI** and **Other translations match** are how similar the saved text is to the MT suggestions, AI suggestions and existing translations shown. Unchanged text is 100%. The API records only the TM match, by source; uploads record no match at all, so an uploaded translation is always No match, at 100% of the Full translation rate.
- *The row:* each match is looked up in its own scheme, matches outside every row drop out, and the **cheapest** remaining row wins (ties: TM, MT, AI, Other); none left is No match at 100%. Cost = units × Full translation rate × row percentage.
- *Approvals:* one paid approval per approver, string, language, plural form and source version, at the Proofread rate per unit. With category-based approval rates (on by default on the page), an approval is priced as an identical translation at the 100% row of the approved translation's category: TM perfect stays perfect (TM 100% with Use edit distance for TM Net Rate Scheme), other TM matches use TM 100%, and an approved No match translation uses Other translations 100%. An approved TM, MT or AI pre-translation is priced in its engine's 100% row, so the AI 100% approval bucket holds approvals of AI pre-translations, automatic ones included, and of translations whose cheapest row was AI. With flat rates, approvals are one total at the Proofread rate and cannot be told apart by origin.
- *Exclude approvals for edited translations* drops an approval when the approver has any translation record on the same string, language and plural form: at any time, by any method (including an upload or a pre-translation run under their account), whichever version they approved.
- *Use specific categories for auto-translations* (on by default on the page): when the closest existing translation is a pre-translation, the Other translations match is priced in the TM, MT or AI scheme instead.
- *Use edit distance for TM Net Rate Scheme* changes how the TM match is measured (see Matches). The perfect row is not used: every TM match is capped at 100%, also for approvals priced with category-based approval rates. Translations saved before the option existed, saved with no TM suggestion in the Editor, or added through the API fall back to source similarity, still capped at 100%. The option changes only Translation cost's TM rows, and with them its Savings and Weighted; Cost estimate is unaffected.
- *Savings:* for the first translation of each string (per language, plural form and source version) across all people, not counting pre-translations, Full translation rate × units × (100% − row percentage); plus the full value of an approved pre-translation when nobody had translated the string before it was approved. Later translators of the same string add no savings. Despite the name, Other translations matches count too. The savings of approved pre-translations appear only in the result's `savings.total`, not in its TM, MT, AI or Other rows, so the total can exceed the sum of the rows, and the AI row never includes AI pre-translation. Savings are gross: the AI provider's bill is not subtracted. A pre-translation's saving is added when it is approved but dated by the pre-translation, so the savings of past periods grow over time, and a rerun of an old period can differ from its archive.
- *Task mode:* the work of everyone, not only assignees, on strings ever in the task, in the task's language, from the task's creation until now. A task created with **Create Translation Cost Report** and a rates template gets this as its Actual cost when it becomes Done or Closed; a newer task report generated by a manager and saved to the archive replaces it. Through the API `taskIds` cannot be combined with dates, members or languages (in a project, nor with files and labels), so task mode cannot answer 'this year' or one person's share. Each task is priced on its own: work on strings that are in two selected tasks, such as a translation task and its proofreading task, is counted in both, so never add such tasks' totals. `get_project_task` returns the saved `actualCost` and `estimatedCost`; the estimate is a Cost estimate, not spend.

**Common questions.**
- *A string has several translations.* Every person who saved a translation of it is paid once for it, whether their translation was approved, top-voted, or later deleted. Votes are not read. Three translators on one string are three paid translations. There is no setting to pay only for the approved translation, and Top members' Winning does not replace one: it is source volume with no rates and no TM, MT or AI rows, dated by the approval, counted once per approver, and kept after the approval is removed. One string can also have several approved translations: on Enterprise each proofreader holds one approval per string, language and plural form, so two proofreaders can approve two different translations; on crowdin.com each proofreading step holds one. So do not offer Winning, an export or another report as a way to pay only for approved work; if paying several translators for one string is the concern, the fix is in how the work is assigned (one translator per string), not in the report. What the extra translations cost can be rebuilt as an estimate (`references/reports/translation-cost-figures.md`).
- *The string was translated in different ways.*

| How | Paid? | Row |
|---|---|---|
| Typed by hand in the Editor | yes, to the translator | the cheapest that applies: TM by source match (with Use edit distance, by similarity to the TM translations shown), MT, AI or Other by similarity to what was shown; otherwise No match |
| TM suggestion inserted | yes | TM row of the source match (with Use edit distance: TM 100% if unchanged, the row of the remaining similarity if edited), unless a cheaper row applies |
| MT or AI suggestion, unchanged | yes | MT or AI 100%, unless a cheaper row applies |
| MT or AI suggestion, edited | yes | the MT or AI row of the remaining similarity (a higher percentage than the 100% row), unless a cheaper row applies |
| A pre-translation edited in the Editor | yes | Other translations by similarity to it; TM, MT or AI with Use specific categories for auto-translations |
| TM, MT or AI pre-translation, also one added through the API as pre-translated | no | Auto-translated only |
| Uploaded translation file | yes, to the uploader | No match (100%) |
| Added through the API | yes, to the token's owner | TM row by source match (at most TM 100% with Use edit distance) or No match |

- *Several people, or one person several times.* Each person is paid once per string. A later translator's text is compared with the translations already there, so it often lands in a cheaper Other translations row. A later translation unlike the others is not therefore No match: by default it still gets the TM row of its source match, or an MT or AI row; No match is only when no row applies. One person re-translating, or editing their translation in place with Replace in translations, is not paid again, and their match values stay as written at their first save: later saves never update them.
- *Approvals.* Each approver is paid once, even across several workflow steps, at the Proofread rate or, with category-based approval rates, at the 100% row of the approved translation's category; approving again adds nothing. Removing the approval or deleting the approved translation does not take the payment back. Self-approval is paid unless Exclude approvals for edited translations is on.
- *Deleted and hidden strings* still count, including strings deleted from files in the file filter. Work in the project's source review language does not.
- *Which date.* Translated in March and approved in May: the translation is in March's report, the approval in May's.

**crowdin.com and Enterprise.** Same calculation; crowdin.com has the project level only and names the option Use category-based proofread rates. Enterprise adds the workspace level (grouped by member or language, a person's work is summed across projects; grouped by project, each project shows separately with its languages and members, with the same cost totals; Weighted units are rounded up per row, so their total can come out slightly higher) and the Workflow step filter, which keeps strings linked to that step without checking at which step the work was done; on steps after Switch source language, the intermediate language's text is the source.
