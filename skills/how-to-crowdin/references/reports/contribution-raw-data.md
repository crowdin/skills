# Contribution raw data

This file covers only what cost questions need from this report: what its rows hold, and how to rebuild from them what repeat translators or source changes cost.

**What it shows.** One row per person, string, language, plural form and source version, from the same record of actions as Translation cost, deleted translations included. It is project level and API only (`generate_report_contribution_raw_data`, `contribution-raw-data`): there is no workspace or organization version, so export project by project. It has no rates, costs, edit-distance TM match, or mark of which translation was a string's first, and it covers the project's current target languages only.

**Columns.** Modes: `translations`, `approvals`, `votes`. Columns: `userId`, `languageId`, `stringId`, `translationId`, `pluralForm`, `sourceStringTextHash` (the source version), `preTranslated` (Yes for TM, MT and AI pre-translations), `mtEngine`, `tmName` and `aiPromptName` with their ids, `tmMatch` (`perfect` above 100), `mtMatch`, `aiMatch`, `suggestionMatch`, `sourceUnits`, `targetUnits`, `createdAt` (the first save, UTC) and `updatedAt`; `approvals` adds `wasEdited` (the approver approved their own edit of an existing translation), `votes` adds `mark`. `fileId` and `filePath` exist only in file-based projects, `branchId` and `branchName` only in string-based ones, units are rejected with the strings unit, and one invalid column rejects the request.

**What repeat translators or source changes cost.** No report gives either number: rebuild it from this report and call it an estimate. Per project, export the `translations` mode in the unit of the confirmed rates, with no `dateFrom` so earlier versions are visible, drop rows with `preTranslated` = Yes, key the rest by `stringId`, `languageId` and `pluralForm`, and order each key by `createdAt`.
- *Several translators:* within one key and one `sourceStringTextHash`, the first row is the translation that was needed and every later row created in the period is extra. Split the extras into edits by the person who approved that key (an `approvals` row of the same user; `wasEdited` = Yes is the clearest case) and parallel work. An extra that reuses the existing translation lands in a cheap Other translations row, but a parallel translation with different text is priced near the Full translation rate: do not call the extras discounted before the priced rows show it.
- *Source changes:* when a key has an earlier row with another `sourceStringTextHash` (a version that was only pre-translated was never paid, so it does not count), a row on the new hash created in the period is paid again because of the change if it is the first row of that hash or its author also has a row on an earlier hash; other later rows on that hash belong to several translators. In the `approvals` mode the same test on approvers gives the approvals paid again: price them as approvals are priced. Any change of the text, even whitespace or a tag, is a new version, and Crowdin keeps only a hash of earlier versions, not their text, so cosmetic and real changes cannot be told apart and the old text cannot be shown. Translations kept through a change and not saved again cost nothing.
- Price each row as the report does: `sourceUnits` × the member's Full translation rate × the cheapest row its match columns reach. Rebuild the whole period the same way and give the gap to the report's total for the same period and rates: removed target languages are missing from the raw data, and Use edit distance for TM Net Rate Scheme and Use specific categories for auto-translations cannot be reproduced from it. Source content updates gives the changed source volume as context (`references/reports/source-content-updates.md`); never present that volume × languages × rate as this cost.
