# Why a language, file or release was late

Crowdin keeps tasks, strings, translations and approvals with their dates, not a history of a project's progress. Rebuild the timeline from those dates, name each cause as established, likely or unknown, and say what Crowdin does not record. Never fill a gap with a number nobody recorded.

1. **Pin the scope.** Crowdin has no release object, and only tasks have deadlines. Ask for the project, what marks the release (a branch, a label or a batch of tasks) and the deadline, offering candidates from `list_organization_tasks` (`projectIds`, `targetLanguageIds`, `deadlineFrom` and `deadlineTo`), `list_branches` and `list_labels`. Done when you know the strings, the language and the deadline.
2. **Build the timeline from the tasks.** `list_organization_tasks` with `projectIds` and `targetLanguageIds`, for the late language and for one to three languages that were on time (`list_project_tasks` has no language filter). Per task: lead time = `deadline` − `createdAt`; waiting = `startedAt` − `createdAt`; working = `resolvedAt` − `startedAt`; late by = `resolvedAt` − `deadline`; hand-off = a follow-up task's `startedAt` − the `resolvedAt` of the task in its `precedingTaskId`. `originalWordsCount` is the task's size at creation, `wordsCount` its size today. Compare the late language with the on-time ones; for many tasks, Task usage grouped by language (`references/reports/task-usage.md`) gives on-time and overdue counts and average times per language, and its period selects tasks by their creation date. Done when you know which stretch of time made it late.
3. **Check the usual causes** for that stretch: the task was created late; it waited for an assignee or for the previous step; the assignee had other work at the time (`list_organization_tasks` with `assigneeIds`, across projects); the source arrived or changed late (`list_file_revisions`, or string dates through `list_strings` with a CroQL filter, which `croql` writes); pre-translation ran late or not at all (`list_pre_translations`); open issues held strings back (`list_stringasset_comments` with type issue); blockers or reassignments the team wrote down (`list_project_task_comments`). A source change reaches every language, so it explains one late language only together with something specific to that language. Per string, `list_language_translations` and `list_translation_approvals` say when it was translated and approved. Translation activity over 62 days or less shows the shape of the work per day (a late start, a stall, approvals bunched after the deadline), never a ready date; it covers the whole project, every branch and file, and through the API ignores `languageId`, so read the late language's rows from the result and say they include work outside the release.
4. **Workflow (Enterprise).** `list_strings_on_the_workflow_step` shows which strings are at a step now, by language and status; it has no history. `list_translation_approvals` returns each approval's `workflowStepId` and `createdAt`, which date when a string passed a review step, as long as the approval still exists. A project's `workflowId` is its own workflow, not a template: name the steps from `list_workflow_steps`. Steps have no due dates, only tasks do: suggest a deadline on the proofreading task for next time.
5. **Say what Crowdin does not record:** when a string entered a workflow step, or passed a step that leaves no approval; progress on a past date (never rebuild it from Translation activity, which counts every save); a task's status history (only `startedAt` and `resolvedAt` are kept); changes of a deadline. The project's Activity feed has no API, so its events reach you only if the user reads them from the page. API dates are UTC.
